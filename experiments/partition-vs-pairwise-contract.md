# Partition versus pairwise: what changing the matcher's output contract cost

The matcher used to return a list of pairwise verdicts. It now returns a
partition of the block, which is Abzu's contract: every input record placed in
exactly one group. This measures what that cost in accuracy, because the
argument for the change is data integrity rather than accuracy, and a change
made for one reason still has to be honest about the other.

## What changed

|                                      | pairwise                                                                    | partition                                      |
| ------------------------------------ | --------------------------------------------------------------------------- | ---------------------------------------------- |
| Output field                         | `candidates: list[XCandidate]`                                              | `resolved: list[ResolvedEntity]`               |
| What the model writes                | one candidate per matching pair, with every field of both records copied in | one group per entity, ids only                 |
| Can the answer contradict itself     | yes: a-b, b-c, not a-c                                                      | no                                             |
| A record the model omits             | an absent pair nobody counts                                                | a hole in the cover, detected and recovered    |
| Who picks the surviving field values | the model                                                                   | `serf.merge.canonical`, from each field's type |

## Method

Both arms use the per-dataset signatures **untrained**, the same 1,000-record
sample at seed 42, three ER iterations, and the same cluster-based scorer. The
pairwise arm is the `closure_*_iter3` runs already recorded in
`per-dataset-signature-baseline.md`. The only difference between the arms is
what the matcher is asked to return.

```bash
serf benchmark --dataset <ds> --signature-mode per-dataset \
  --sample-records 1000 --seed 42 --max-iterations 3
```

Logs: `/opt/cursor/artifacts/partition_<dataset>_1k.log`, table generated by
`/opt/cursor/artifacts/partition_table.py`.

| Dataset        | F1 pairs | F1 parts |   Delta | P pairs | P parts | R pairs | R parts | FP pairs | FP parts | Conserved |
| -------------- | -------: | -------: | ------: | ------: | ------: | ------: | ------: | -------: | -------: | --------: |
| amazon-google  |   0.8655 |   0.8390 | -0.0265 |  0.8732 |  0.8554 |  0.8580 |  0.8232 |       43 |       48 | 100.0000% |
| abt-buy        |   0.9354 |   0.9318 | -0.0036 |  0.9606 |  0.9804 |  0.9114 |  0.8878 |       19 |        9 | 100.0000% |
| dblp-scholar   |   0.9793 |   0.9665 | -0.0128 |  1.0000 |  0.9870 |  0.9594 |  0.9469 |        0 |        4 | 100.0000% |
| walmart-amazon |   0.9412 |   0.9467 | +0.0055 |  0.9231 |  0.9467 |  0.9600 |  0.9467 |        6 |        4 | 100.0000% |
| dblp-acm       |   0.9737 |   0.9926 | +0.0189 |  0.9747 |  0.9958 |  0.9727 |  0.9895 |       12 |        2 | 100.0000% |
| **mean**       |   0.9390 |   0.9353 | -0.0037 |         |         |         |         |       80 |       67 |           |

**The contract change is accuracy-neutral.** Mean F1 moves by -0.0037, and the
run-to-run variance on these tasks is about 0.01, so the mean change is inside
the noise. Two datasets gain, three lose, and no individual movement except
amazon-google's -0.0265 clears the noise floor by much.

It is worth stating plainly that the first measurement here was DBLP-ACM alone,
at +0.0189, and that reading was wrong. One dataset moving twice the noise
floor is weak evidence, and the five-dataset mean says the effect is
approximately zero. The single-dataset number was the best case, not the
typical one.

Direction of the trade, where it is visible: precision up on three of five
datasets and total false positives down from 80 to 67, recall down slightly on
four of five. Asking for a partition makes the model commit to a grouping, and
committing is a little more conservative than nominating pairs.

**Conservation holds everywhere.** All five runs account for 100.0000% of their
input records, and none needed a record recovered, so the integrity guarantee
is not being bought with silent repairs.

## Two caveats

The prompts were written and A/B-tested against the pairwise contract. Their
domain knowledge carries over unchanged, but the answer-shaping paragraphs were
rewritten for partitions and have not been tuned. GEPA has not run against the
new contract at all. So this table measures a contract change under prompts
fitted to the old contract, which is the pessimistic case for the new one.

These are validation-equivalent samples, not holdout. The 1,000-record sample
at seed 42 is exactly the split `serf train` selects on, so these numbers are
comparable to each other and to the earlier table, but they are not
generalization estimates. See `.cursor/rules/ml-experiments.mdc`, rule 1.

## Bug this found

`abt-buy` failed its first run outright:

```
ValueError: Conservation failed after recovery: FAIL: 1000/1000 input records
reachable (100.0000%), 6 dangling references (0.6889%), 0 claimed twice
```

Coverage was perfect and the run still failed, which is the check working. A
run that merges an already-merged entity leaves the intermediate entity's
minted id in the result's `source_ids`, and the check was reading those as
references to records that never existed. The ids are real lineage — each
identifies an entity that existed — so the check is now told which ids the run
minted, rather than the lineage being trimmed to make the check pass. Trimming
would have destroyed the audit trail to satisfy the thing auditing it.

`serf benchmark` now uses one id allocator for a whole run, which also makes it
impossible to mint the same id in two iterations.
